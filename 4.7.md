**Question 7:**
Relation variable **NADDR** with attributes **NAME** (Unique), **STREET**, **CITY**, **STATE**, **ZIP** specifies that:
1.  For each ZIP code, there is only one CITY and one STATE.
2.  For each STREET, CITY, and STATE, there is only one ZIP code.

**a) Provide a minimal (irreducible) set of functional dependencies for this relation variable. Also specify the candidate key(s).**

**Step 1: Identify Functional Dependencies from the text**
*   "NAME is unique": This implies that NAME uniquely identifies a record.
    *   $NAME \to STREET, CITY, STATE, ZIP$
*   "For each ZIP code, there is only one CITY and one STATE":
    *   $ZIP \to CITY$
    *   $ZIP \to STATE$
*   "For each STREET, CITY, and STATE, there is only one ZIP code":
    *   $STREET, CITY, STATE \to ZIP$

**Step 2: Simplify to Minimal Cover**
1.  **Decompose RHS:**
    *   $NAME \to STREET$
    *   $NAME \to CITY$
    *   $NAME \to STATE$
    *   $NAME \to ZIP$
    *   $ZIP \to CITY$
    *   $ZIP \to STATE$
    *   $STREET, CITY, STATE \to ZIP$

2.  **Remove Redundant FDs (using Transitivity):**
    *   Since $NAME \to ZIP$ and $ZIP \to CITY$, the dependency $NAME \to CITY$ is redundant (transitive).
    *   Since $NAME \to ZIP$ and $ZIP \to STATE$, the dependency $NAME \to STATE$ is redundant.
    *   Remove $NAME \to CITY$ and $NAME \to STATE$.

3.  **Check LHS attributes for extraneous attributes:**
    *   $STREET, CITY, STATE \to ZIP$: We cannot remove STREET (Street alone doesn't determine ZIP), CITY, or STATE.
    *   All other LHSs are single attributes.

**Minimal Cover ($F_c$):**
$$F_c = \{ NAME \to STREET, \ NAME \to ZIP, \ ZIP \to CITY, \ ZIP \to STATE, \ \{STREET, CITY, STATE\} \to ZIP \}$$

**Candidate Keys:**
*   **NAME**: Since NAME is unique and determines all other attributes (directly or indirectly), it is a Candidate Key.
*   **Other Keys?** The set $\{STREET, CITY, STATE\}$ determines $ZIP$, which determines $\{CITY, STATE\}$. However, this set does not determine $NAME$ (multiple people can live at the same address, and the problem doesn't state the reverse). Since it doesn't determine all attributes, it is not a superkey.
*   Therefore, the only Candidate Key is **{NAME}**.

**b) Is the relation variable in BCNF? If not, provide a better design.**

**BCNF Check:**
A relation is in BCNF if for every non-trivial functional dependency $X \to Y$, $X$ is a superkey.

*   Check $ZIP \to CITY$:
    *   Is $ZIP$ a superkey? The closure of $ZIP$ is $\{ZIP, CITY, STATE\}$. It does **not** include $NAME$ or $STREET$.
    *   Since $ZIP$ is not a superkey, this violates BCNF.
    *   *Answer: No, NADDR is not in BCNF.*

**Better Design (Decomposition):**
We must decompose the relation to resolve the violation $ZIP \to CITY, STATE$.

We split the original relation **NADDR(NAME, STREET, CITY, STATE, ZIP)** into two relations based on the violating dependency:

1.  **Relation R1 (Location Info):**
    *   Attributes: $ZIP, CITY, STATE$
    *   Functional Dependency: $ZIP \to CITY, STATE$
    *   Key: $ZIP$ (This is in BCNF)

2.  **Relation R2 (Name & Address Info):**
    *   Attributes: $NAME, STREET, ZIP$ (We include ZIP to link back to R1)
    *   Functional Dependency: $NAME \to STREET, ZIP$
    *   Key: $NAME$ (This is in BCNF)

**Final Schema:**
*   **ZIPS(ZIP, CITY, STATE)**
*   **ADDRS(NAME, STREET, ZIP)**
