
**Answer to Question 15: Concurrency Control**

**1. Overview**
Concurrency control is the process of managing simultaneous operations on a database without allowing them to interfere with one another. Its primary goal is to ensure **isolation**, meaning that even though multiple users are accessing the database at the same time, each transaction operates as if it were the only one running on the system. This preserves the **consistency** and **integrity** of the data.

**2. How Concurrency Control is Currently Done**
To prevent the "interference of updates" (such as the Lost Update problem, Dirty Reads, or Inconsistent Retrievals), modern Database Management Systems (DBMS) use several standard techniques. These methods ensure that the final state of the database is the same as if the transactions had been executed sequentially (one after the other), a property known as **Serializability**.

The most common methods currently used are:

*   **Locking (Pessimistic Concurrency Control):**
    This is the traditional approach where a transaction "locks" data to prevent others from accessing it while changes are being made.
    *   **Shared Lock (S-lock):** Allows other transactions to read the data but not modify it.
    *   **Exclusive Lock (X-lock):** Allows the transaction to both read and write the data; no other transaction can read or write it.
    *   **Two-Phase Locking (2PL):** This is a protocol to ensure serializability. It has two phases: the *Growing Phase* (where locks are acquired) and the *Shrinking Phase* (where locks are released). Once a transaction releases a lock, it cannot acquire any new ones.

*   **Multiversion Concurrency Control (MVCC):**
    This is widely used in modern systems (like PostgreSQL and Oracle) to improve performance. Instead of locking the data row and making other users wait, the DBMS maintains multiple **versions** of a single data item.
    *   When a user wants to read data, they see the version that was committed at the start of their transaction (a "snapshot").
    *   When a user updates data, they create a new version without overwriting the old one immediately.
    *   This allows "readers" to never block "writers" and vice-versa, solving the interference issue without heavy locking.

*   **Timestamp Ordering:**
    Transactions are assigned unique timestamps based on their start time. The system ensures that if a transaction $T_A$ has an older timestamp than $T_B$, the database behaves as if $T_A$ executed completely before $T_B$. If a conflict is detected (e.g., a younger transaction tries to overwrite an older one), the younger transaction is aborted and restarted.

*   **Optimistic Concurrency Control:**
    Unlike locking, this method assumes that conflicts are rare. Transactions execute without restrictions. However, just before committing, the DBMS checks to see if any data used by the transaction was modified by another transaction during its execution. If a conflict is found, the transaction is rolled back and retried.

**3. Examples of Databases Supporting These Methods**
Almost all modern relational and many non-relational databases support these concurrency control mechanisms:

*   **PostgreSQL:** Uses **Multiversion Concurrency Control (MVCC)** as its primary mechanism, ensuring that readers never block writers.
*   **Oracle Database:** Heavily relies on **MVCC** for high concurrency and data consistency.
*   **MySQL (InnoDB Engine):** Uses a combination of **MVCC** and **Row-level Locking** to handle concurrent transactions.
*   **Microsoft SQL Server:** Supports both **MVCC** (via Snapshot Isolation) and traditional **Locking** (Pessimistic).
*   **MongoDB:** Utilizes **Multi-granularity Locking** (locking at the document, collection, or database level) and supports snapshot isolation for multi-document transactions in newer versions.
